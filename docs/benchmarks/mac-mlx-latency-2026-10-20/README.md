# Index 9B: проверка задержек и постоянный процесс Mac Lab

20 октября 2026. Изменено только отдельное тестовое приложение
Kat Translation Lab. Основное приложение, MLX-runtime, веса,
подсказки, MTP2 и параметры генерации не менялись.

**Причина исторических 12,49 секунды пока не установлена.** В трёх новых
контрольных сериях, всего 192 перевода, такой выброс не воспроизвёлся.
Подтверждена и устранена другая задержка тестового окна: повторная
загрузка всей модели при каждом нажатии.

## Что проверено

Тот же Mac M3 Pro / 18 GiB, тот же установленный MLX-пакет и синтетический
корпус из 16 RU↔EN примеров. Последовательные запуски:

| Контроль | Запросов | Максимум генерации |
|---|---:|---:|
| С профилированием этапов, памяти и GC | 64 | 2,121 с |
| Исходный runner без профилирования | 64 | 2,150 с |
| Повтор прежней последовательности Apple → 2B → профилируемый 9B | 64 | 2,407 с |

Во всех 192 случаях результат посимвольно совпал с историческим
переводом того же примера. Нет подтверждения, что причина выброса —
изменение текста, накопление контекста или ухудшение декодирования.

В профилируемых сериях:

- Активная память MLX после каждого запроса — одинаковые
  **5 223 155 730 байт**. Рост активных аллокаций между запросами
  в этих сериях не обнаружен.
- Максимальный зарегистрированный GC — **2,72 мс**.
- В обычных запросах основное время заняли шаги генерации;
  создание генератора — доли миллисекунды, закрытие — около 10 мс.
- Профилировщик сохраняет CPU/полное время, первую выдачу,
  события генератора, статистику MTP, память и страничные ошибки.
  Полные пооперационные трассы остались в `.build`; в отчёте события
  агрегированы по этапу без удаления запросов.

Эти факты относятся к **новым нормальным прогонам**. Они не доказывают,
что в историческом выбросе не было конкуренции за GPU, давления памяти
или ограничений планирования/питания. Снимки `pmset` не показали записанных
предупреждений; swap во время диагностики менялся. Изолированного контроля
всех фоновых процессов и температур не было. Объявлять конкретную причину
12 секунд на этих данных нельзя.

Начальный диагностический опыт с таймером `faulthandler` сам завис
при отмене снятия стека. Native sample указал на
`faulthandler_cancel_dump_traceback_later_py` / ожидание блокировки;
этот неполный опыт исключён из таблицы. Таймер удалён из сохранённого
профилировщика. Это отдельный дефект инструмента наблюдения, не
воспроизведение исходных 12 секунд.

## Исправление тестового окна

Раньше каждый перевод запускал Python, импортировал библиотеки,
загружал веса, переводил и завершал процесс. Теперь один процесс
обслуживает последовательные запросы с одной выбранной моделью.
**Новый генератор и новый контекст создаются для каждого перевода** —
история предыдущего запроса не добавляется.

Модель выгружается по умолчанию после 5 минут простоя, при смене движка,
нажатии «Выгрузить Kat»/«Стоп» или закрытии окна. Перед загрузкой
другого движка приложение дожидается завершения предыдущего процесса.
Ручной текст не записывается в файлы. В настройках доступно 1–60 минут,
в том числе 5 и 10; выбор сохраняется между запусками. Изменение таймера
передаётся уже загруженному процессу без перезагрузки модели; во время
перевода оно откладывается до завершения запроса.

На одном синтетическом примере про Анну, с измерением от отправки
запроса до ответа:

| Режим | Полное ожидание |
|---|---:|
| Старый способ: новый процесс, медиана 3 запусков | **5,458 с** |
| Новый способ: первый запрос | **4,780 с** |
| Новый способ: готовая модель, медиана 4 запросов | **0,882 с** |

Повторные запросы в этом опыте быстрее примерно **в 6,19 раза**.
Это сокращение времени повторной инициализации, а не ускорение
математики 9B в шесть раз. Первый запуск по-прежнему дорогой.
Этот результат **не означает исправления исторического выброса генерации**.

## Проверки

- Регрессионный тест сначала упал: runner не поддерживал постоянный режим.
  После реализации 32 перевода (два прохода корпуса) совпали с прежними
  результатами; первая загрузка положительна, остальные равны нулю.
- Некорректный запрос возвращает ошибку; следующий корректный запрос
  успешно переводится. EOF завершает процесс с кодом 0.
- В первоначальном варианте процесс завершился через **60,22 с** простоя.
  Затем добавлена настройка: проверены исходные 300 с, смена на 600 с
  без повторной загрузки и неизменность текста. Нулевое, чрезмерное,
  строковое и логическое значения отклонены. Для быстрой проверки
  завершения установлен тестовый таймер 2 с; измерение в idle-settings.json.
  Полные 5/10 минут ожидания отдельно не выдерживались.
- Прерывание во время генерации и следующий запуск проверены.
- Из пересобранного SwiftUI-приложения последовательно вызваны 2B, 9B,
  затем 9B повторно: `model_reused=true`, загрузка 0, одинаковый текст.
  При повторном запросе таймер изменён на 600 с без повторной загрузки,
  после проверки восстановлен настроенный интервал. Свежие времена в JSON.
- Сборка приложения, ad-hoc подпись, Python compile, свежий регрессионный
  тест, запуск сохранённого профилировщика и EN/RU docs parity проверены.

Посимвольное совпадение установлено для корпуса. Изменение не затрагивает
модель или алгоритм, однако это не самостоятельная оценка качества
на всех языках. Не проверялись Store-сборка, телефоны, OCR и голос.

## Что остаётся

Поймать именно длительный выброс со стеком и системными метриками
в момент его возникновения. Сохранённый
[профилировщик](../../../scripts/research/macos-translation-lab/profile_mlx.py)
даёт повторяемую исходную точку. Задача причины 12 секунд остаётся
открытой в BACKLOG; повторная загрузка тестового окна исправлена отдельно.
