# Whisper на iOS и macOS: Core ML, MLX и Q8 — 20 октября 2026

**На проверенном iPhone 17 Pro лучший вариант — Core ML-энкодер с Q8-декодером: примерно в 1,8–2 раза быстрее текущего F16, с тем же текстом на трёх записях.** Память процесса увеличилась примерно с 1,91 до 2,35 ГБ. На Mac M3 Pro обычный Core ML не ускорил распознавание; MLX Python выиграл 9–16%, но изменил расшифровку длинной русской записи. В Kat ничего не включено.

Числа и проверяемое происхождение: [results.json](results.json), [provenance.json](provenance.json), [проверки](verification.json). [Стенд и инструкции](../../../scripts/research/apple-whisper-acceleration/README.ru.md).

## Условия

- Mac M3 Pro, 18 ГБ RAM; физический iPhone 17 Pro, 12 ГБ RAM.
- Один Whisper **large-v3-turbo**, производственный F16-файл и производные от именно этих весов. whisper.cpp `927cfce34f31707e17f2bff35c349632fb9e2c3a` / v1.9.4.
- Три настоящие записи: две ранее предоставленные русские — **7,90 и 25,18 с**; публичный `jfk.mp3` из whisper.cpp — **11,00 с**, английский. Синтетической речи нет. Частные аудио и расшифровки не публикуются.
- Для всех вариантов одинаковый mono 16 kHz Float32 PCM, явный язык, greedy/temperature 0. Native: Metal, Flash Attention, четыре потока, без предыдущего контекста и temperature fallback. Опциональное исправление дат выключено.
- iPhone-стенд использовал тот же increased-memory-limit entitlement и `GGML_METAL_NO_RESIDENCY=1`, что и Kat; Metal оставался включённым.
- Измеряется только распознавание. Запись микрофона, предварительная обработка в Kat, перевод, TTS и полный голосовой цикл сюда не входят.
- Загрузка модели отделена от распознавания. В каждом процессе первый проход всех трёх записей — прогрев; затем три измеренных прохода с чередованием порядка записей.
- Mac: два блока с обратным порядком вариантов, шесть измерений на запись; CPU+Neural Engine — отдельный контроль из трёх. Других исследовательских GPU-процессов во время этих замеров не было. Native thermal state — nominal; для Python MLX поминутное состояние не снималось, системных thermal/performance warnings перед серией не было.
- iPhone: первая компиляция Core ML прогрела устройство. Ожидание nominal в течение 300 секунд завершилось неудачей и **не включено** в результаты. Ниже используются только измерения, у которых **thermal state = fair (1) до и после** распознавания. Для F16/Q8 — по три; Core ML, Core ML+Q8 и Swift FP16 — по шесть; остальных — по три на запись. Более холодные контрольные измерения сохранены отдельно; последний F16-контроль снова был nominal и не смешан с fair.
- Одинаковая категория thermal state не гарантирует одинаковую температуру или частоту. Это небольшая серия на рабочих устройствах, а не измерение с фиксированными частотами. Разницу в несколько процентов не следует считать устойчивым общим ускорением.

## iPhone: медиана распознавания, секунды

| Вариант | RU 7,90 с | RU 25,18 с | EN 11,00 с | Память процесса, ГБ |
|---|---:|---:|---:|---:|
| Текущий F16 / Metal | 1,077 | 1,520 | 1,177 | 1,91 |
| Q8 / Metal | 1,168 | 1,444 | 1,219 | 1,10 |
| Core ML + F16 | 0,639 | 1,054 | 0,673 | 3,13 |
| **Core ML + Q8** | **0,571** | **0,837** | **0,593** | **2,35** |
| Swift MLX, upstream | 1,844 | 3,319 | 2,004 | 3,27 |
| Swift MLX, эксперимент FP16 | 0,774 | 1,210 | 0,799 | 2,46 |
| Core ML, только CPU/Neural Engine + F16 | 1,090 | 1,285 | 0,790 | 3,14 |

Core ML+Q8 сократил задержку на **45–50%** относительно F16. Q8 отдельно сохранил около **0,81 ГБ памяти**, но выигрыш скорости есть только на длинной записи. Принудительный CPU/Neural Engine хуже автоматического выбора Core ML на этих примерах.

Swift MLX проверен в отдельном iPhone-приложении, а не перенесён из Mac-результатов. В upstream-реализации Float32 мел-признаки и вычисляемые positional embeddings повышают точность вычислений энкодера. Эксперимент сохраняет их в Float16; он ускорил этот Swift-вариант примерно в **2,4–2,7 раза**, снизив память процесса с 3,27 до 2,46 ГБ. Его результат всё равно медленнее Core ML+Q8.

## Mac: медиана распознавания, секунды

| Вариант | RU 7,90 с | RU 25,18 с | EN 11,00 с | Память процесса, ГБ |
|---|---:|---:|---:|---:|
| Текущий F16 / Metal | 0,762 | 1,018 | 0,796 | 1,97 |
| Q8 / Metal | 0,787 | 0,974 | 0,808 | 1,15 |
| Core ML + F16 | 0,794 | 1,066 | 0,820 | 2,14 |
| Core ML + Q8 | 0,756 | 0,962 | 0,791 | 1,39 |
| **MLX Python / F16** | **0,683** | **0,860** | **0,723** | — |
| Core ML, только CPU/Neural Engine + F16 | 1,059 | 1,331 | 1,153 | 1,85 |

На этом Mac Core ML+F16 медленнее baseline; Core ML+Q8 близок к нему, с небольшим выигрышем на длинной записи. Q8 полезнее экономией памяти, чем скоростью. MLX Python быстрее на **9–16%**; для него в JSON отдельно сохранены peak RSS и MLX allocation peak, которые нельзя подставлять вместо physical footprint.

Все значения памяти в таблицах — **максимум выборочных измерений physical footprint процесса**, десятичные ГБ. Это не непрерывно измеренный пик всей системы. Отдельные сервисы Core ML не входят в эту метрику; GPU-allocations не складываются с ней, поскольку память может пересекаться.

## Качество

**Совпадение с F16 не означает правильность.** Для частных записей не создавался независимый человеческий эталон, поэтому WER для них не вычислялся. В JSON показаны точное совпадение и расстояние между нормализованными словами относительно F16; последнее не является WER.

- Q8 совпал с F16 на всех трёх записях и обеих платформах.
- На iPhone Core ML+F16 и Core ML+Q8 также совпали с F16 на всех трёх записях во всех включённых повторах.
- На Mac автоматический Core ML изменил только пунктуацию длинной записи: нормализованные слова и числа совпали. Принудительный CPU/Neural Engine дал одно отличие на уровне нормализованных слов.
- MLX Python на Mac изменил длинную запись: пропало приветствие, название модели стало записано фонетически, время потеряло разделитель. Получилось восемь операций редактирования относительно F16 после нормализации; это **не восемь доказанных ошибок относительно речи**. Равенство качества не установлено.
- Swift MLX с FP16 и без него сохранил одинаковый между ними текст: отличия от F16 — пунктуация, предлог перед временем и его оформление. Один нормализованный токен отличается.
- На короткой русской записи **все варианты сохранили прежнее ошибочное объединение времени и даты**. Оптимизация вычислений эту проблему не исправила.
- На английском JFK все варианты дали 0 ошибок по известному эталону из 22 слов после удаления пунктуации и приведения регистра. Один короткий английский пример не характеризует общую точность.

## Загрузка, размер и применимость

| Веса | Размер |
|---|---:|
| F16 GGML | 1,625 ГБ |
| Q8 GGML | 0,874 ГБ |
| MLX F16, только веса | 1,614 ГБ |
| Дополнительный Core ML-энкодер | 1,275 ГБ |
| Q8 + Core ML-энкодер вместе | 2,149 ГБ |

Q8 уменьшил исходный файл на **46,2%**. Для проверенного Core ML+Q8 требуются и GGML-файл, и отдельный энкодер: суммарно примерно на **0,525 ГБ больше**, чем нынешний F16. Здесь энкодер работает через Core ML с FP16, а native-декодер — с Q8; это не полностью восьмибитный Core ML.

Первое открытие Core ML после установки стенда занимало на iPhone **21,7–25,3 с**, контроль CPU/Neural Engine — **31,1 с**. Повторная загрузка автоматического Core ML занимала примерно **0,4–0,8 с**. На Mac первая загрузка — **5,57 с**, повторная — **0,84 с**. Это существенно для первой подготовки распознавания. «Новый процесс» здесь не означает холодный файловый кеш; процесс загрузки мог использовать кеши ОС и Core ML.

Core ML — перспективный следующий опыт для iPhone, особенно в сочетании с Q8, но дополнительную память нужно проверять одновременно с реальным переводчиком и озвучкой. Для Mac оснований заменять нынешний Metal на Core ML по этим данным нет. MLX и Q8 остаются отдельными кандидатами с разными компромиссами; для решения о включении нужна более широкая выборка голосов, шумов, языков и длинных записей.

## Сохранность и воспроизведение

Исходники Kat, проекты, каталоги, производственные веса и runtime-библиотеки не изменены. SHA-256 исходного F16 и обеих производственных Apple Whisper-библиотек совпали до/после. Vendor checkout whisper.cpp остался чистым. Модели/записи копировались только в контейнер отдельного `Whisper Research`; после тестов этот стенд удалён. Основная Kat не переустанавливалась, не запускалась для тестов, её контейнер, настройки и история не использовались.

Изолированные native Mac/iPhone и Swift MLX Release-сборки прошли; все завершённые распознавания и их расшифровки сохранены локально. Частные логи и сборки находятся в игнорируемой `.build/apple-whisper-acceleration-2026-10-20`, в публичных материалах — только метрики и хэши. Энергопотребление, полный пользовательский голосовой цикл, другие устройства и глобальная многоязычная точность не измерялись.

Первичные реализации: [whisper.cpp Core ML и квантование](https://github.com/ggml-org/whisper.cpp/tree/927cfce34f31707e17f2bff35c349632fb9e2c3a), [MLX Whisper](https://github.com/ml-explore/mlx-examples/tree/main/whisper), [проверенный Swift MLX](https://github.com/Blaizzy/mlx-audio-swift/tree/a5506c1c7978aeea9a3295f83d43beff3f06bcdf). Наличие Core ML не доказывает, что весь энкодер исполняется на ANE; отдельный контроль разрешал только CPU и Neural Engine. Процент размещения операций на ANE не профилировался.
